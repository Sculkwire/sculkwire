# Changelog

Release notes for sculkwire. Each `## vX.Y.Z` section becomes the GitHub release text when its tag is pushed.

## Unreleased

- sculkwire no longer runs rgl. Before, `game_launch`, `game_reload`, `validate_pack`, `bds_check`, `gametest_run` and the server sessions copied a Regolith project to a temp folder and ran a plain `rgl run` on its `default` profile there. That ignored the profile and the flags a project needs (`--compat`), built again what `rgl watch` had already built, and `game_launch` and `game_reload` then replaced the folder rgl exported to with that build. Now, when the profile runs filters, every tool reads what your own rgl last built, `.regolith/tmp/BP` and `.regolith/tmp/RP`, and never writes, moves or deletes it. Run `rgl run`, or keep `rgl watch` running, first, and again after editing the sources. See [Regolith Projects](docs/tools.md#regolith-projects).
- `game_launch` and `game_reload`: a pack rgl exported into the game's `development_*_packs` is used in place, with `--compat` too. A build rgl exported elsewhere (a `local` or `exact` target, the com.mojang folder of another install) is copied into a `sculkwire_*` folder, again on every reload. When rgl has not built the project, the launch fails before the game starts, and the reload fails before `/reload` runs, with the step to take. A folder rgl exported to is never written or deleted any more, for a profile without filters too: before, `game_reload` copied the source packs into it and a second export sharing the uuid was deleted; now the second one is reported as a `client.duplicate-pack-uuid` warning, and a `client.rgl-export-differs` warning says when the folder no longer matches the source packs of a profile without filters.
- `validate_pack`: the `regolith` part of the result gains `builtAt` (when rgl last ran, if it can be told) and always has a `message`. When rgl has not built the project, the source packs are validated and `config.json` gets a `regolith.not-built` warning (an error with `regolith: "build"`); when its output lacks one pack, the warning names that pack. The `regolith.build-failed` diagnostic no longer exists.
- `bds_check`, `gametest_run` and `bds_session_start`: when rgl has not built the project, no server starts and the error is `regolith.not-built` (was `regolith.build-failed`); the `status` of `bds_check` is `not-built` (was `build-failed`). A session `reload` no longer builds: with `rgl watch` running it loads the edited sources, and it follows rgl's output when another profile exported somewhere else.
- A pack folder that `config.json` does not name (an example pack below the project) no longer stops `game_launch` and the server tools for a project whose profile runs filters: it is left out, since rgl does not build it.
- `sculk doctor` no longer checks for rgl, since sculkwire does not run it.

## v0.1.3

- Windows Firewall no longer asks for permission on every Bedrock Dedicated Server run. A server now runs from a stable slot folder, `bds-instances/slot-<n>` in the data folder (the lowest free slot), so `bedrock_server.exe` keeps its path and Windows asks at most once per slot. Before, every run used a new folder, which Windows treated as a new program. A kept instance folder is moved to `bds-instances/<id>`.
- On Windows, `sculk setup` and `install.ps1` add inbound firewall rules named `sculkwire BDS` for the server in slots 0 to 3 (allowed on private and domain networks, blocked on public ones), with one elevation prompt. When the rules exist, setup asks nothing; a declined prompt leaves setup successful. `sculk setup --no-firewall` (`install.ps1 -NoFirewall`, `SCULKWIRE_NO_FIREWALL=1`) skips the step. See [Install and Update](docs/install.md#windows-firewall).
- An update from v0.1.2 does not add the firewall rules, since an update never runs `sculk setup`: Windows asks one last time per slot folder, or run `sculk setup` once to add them. `sculk doctor` on Windows has a `firewall` line that says whether the rules are in place.
- The free-port probe for a new server binds loopback instead of all interfaces.

## v0.1.2

- `game_worlds` (and `sculk game worlds`) lists every world of the active game user, marking sculkwire's test worlds, kept ones and the loaded one, and deletes one test world. It refuses the user's own worlds and the world the game has loaded.
- `game_launch` takes `keep`, to continue in the existing test world instead of replacing it, and `copyFrom`, to start from a copy of one of the user's worlds. The original is never changed; the copy is single player with cheats on.
- `game_launch` removes test worlds nobody played for 3 days (never kept or copied ones, never the one it launches) and lists them in `prunedWorlds`. Before, every world name left a `sculkwire-` world behind for good.
- `sculk bench` holds the input lock on the engine route while each run plays, as `player_act` does, so the user's keyboard and mouse cannot disturb a measured run. F9 takes control back; a `play` run then waits until control returns. The keyboard route is unchanged.
- `sculk bench` with an unknown option prints the reason and the usage and exits 2; before, it printed a stack trace.
- `game_builds`, `game_vanilla_packs` and `game_extract_pack` look for the mcbe-gdk-installer game folder under `SCULKWIRE_GDK_ROOT`, else `$XDG_DATA_HOME/mcbe-gdk-linux`, as `game_launch` already did. Before, they searched only `~/.local/share/mcbe-gdk-linux`.
- `sculk bds run`: a `reload` or `reload all` typed on stdin rebuilds a Regolith project first, as `bds_session_command` does, so the reload loads the edited sources.
- The helper pack deployed into test worlds holds only what the game loads (`manifest.json`, `scripts/main.js`); before, its unit test files were copied too.
- An empty `XDG_DATA_HOME`, `XDG_CACHE_HOME` or `XDG_CONFIG_HOME` counts as unset, as the XDG spec says, so the default folder under the home directory is used. Before, an empty value put sculkwire's data, cache and config folders (and the mcbe-gdk-installer folder) relative to the working directory.
- The validator's `reference.function-missing` for a `function` on line 1 of an `.mcfunction` file that starts with a byte order mark points at the right column; before, it was one column too far right.

### Internal

- Shared plumbing lives in `src/core/` (errors, file writes, child processes, CLI entry, MCP results, Regolith builds); every area uses it.
- `src/features.ts` is the one list of built-in features; `src/cli.ts` and the MCP server read it, and `wireFeatures()` connects them instead of import side effects.
- `src/gamefiles/` owns the game on disk: installs, `options.txt`, `level.dat`, world names, Wine and Proton prefixes.
- `src/runtime/engine/` sits below the game client and no longer imports it; the client hands it what it needs. No import cycle is left in `src/`.
- The agent's method names are kept in one table (`src/runtime/engine/methods.ts`), checked by a test against the agent's `METHODS` and the Protocol table of `docs/engine.md`. CI also builds the `debug-rpc` agent and runs the host tests through `native/host-tests.sh`.

## v0.1.1

Published again on 2026-11-12 under the same number, now with the fight, the plan runner and the task steps. An install that already has v0.1.1 keeps the first publication: `sculk update` only moves to a higher version, and an installed version folder is reused. To get this one, delete `versions/v0.1.1` in the sculkwire data folder and the `agent/prebuilt-0.1.1` folder in the sculkwire cache folder, then run the installer again.

- The repository moved to the Sculkwire organization and is public: [github.com/Sculkwire/sculkwire](https://github.com/Sculkwire/sculkwire), mirrored read-only to [gitlab.com/sculkwire/sculkwire](https://gitlab.com/sculkwire/sculkwire). The installers, `sculk update --install` and the prebuilt agent download use the new address; installs made from the old address keep updating through GitHub's redirect.
- Removed the optional decision model: the Jev/Kev advisor of `player_act` `play` and of the `game_launch` sign-in recovery, the `decision_status` tool, the `advisor` and `vision` inputs of `play` with its `model`, `latency` and `advice` result fields and the per-step `by`, `fallback`, `state`, `answers` and `decisionMs`, the `latency` of `player_job` progress, the decision-model question and `--decision` flag of `sculk setup` and the installers, and the `decision` and `uv` checks of `sculk doctor`. Measured runs showed no effect on `play`, the sign-in recovery now reads the screen through the in-game agent, and the calling coding agent is the planner. `play` now chooses every tactic with its built-in scores, and a goal its checks cannot verify runs until the time limit. A `decision` section left in `config.json` is ignored.
- `game_command` through the script debugger answers `ok: false` when the output is one of the game's failure messages (`No targets matched selector`, `Function <name> not found.`), read from the installed game's language file. Before, only syntax errors and unknown commands failed.
- `game_launch` and `game_reload` always copy the project into its own pack folder. Before, when only another folder served a pack's uuid (such as another project folder's `sculkwire_*` copy with the same uuids), that folder was used silently and project edits never reached the game; now it is left alone and reported as a `client.duplicate-pack-uuid` warning that says the game may load it instead.
- `script_profile` no longer charges the time between game ticks to a function. The game samples only while script code runs, and the gap after each tick's last sample (up to 50 ms) went to that sample, so the top function's self time was about the whole capture whatever the load: on BDS 1.26.63, a `Dimension::getEntities` aura showed 4997 ms (99.6%) of a 5 s capture when it ran every tick and 3000 ms (60%) when it ran once a second. A sample is now charged at most one sampling interval (new `intervalMs`, at least 1 ms), the rest is the new `idleMs`, and the same aura measures 100 ms (2%) every tick and 5 ms (0.1%) once a second. `selfPercent` stays percent of the capture duration.
- `player_act` aims in third person on the engine route. With `game_thirdperson` 1 or 2, every action that turns the view (`look_at`, `attack`, `fight`, `shoot`, `goto`, a station `interact`) failed with `anchor_missing` (`camera.direct_look`): the agent wrote the view only into first person's camera, whose stored view stops following the player once the third-person camera is active. `input.look` now writes the active third-person (orbit) camera too, by its look mode, so the player looks where it is told from behind and from the front. When no camera the player follows is found the error is `anchor_missing` (`camera.view`), with the cameras it saw.
- `game_ui` and `game_input` through the agent allow `Return`, `space` and a click on the game's idle overlay ("You've been away for a bit", OreUI route `/idle-route`, read live on 1.26.63.1). Before, every such input was refused as an unlisted OreUI page and `Escape` only opened the pause menu over it, so a session that left the game alone for a while could not get back into the world. That an allowed input closes the overlay is not verified live yet.
- `player_act` `fight` returns what it did as `fight` on its result and in its message on both input routes, also when it fails, times out or is preempted: kills by type, swings, hits, misses, critical hits, hits taken, damage taken and time (`killed 3 husk with iron_sword: 11 swings, 6 hits, 5 misses, 1 critical, took 2 hits for 3.5 damage, in 10.4 s`). `play` stats add `misses` and `hitsTaken`, and a preempted fight's trace step lists its numbers.
- Fixed: `fight` reported `killed nothing` when it turned to another mob right after a killing blow (the dying mob stays in the stream for its death animation). Kills now come from the helper's death log since the fight started.
- `sculk bench combat --scenario husks3`: 3 husks in a tight group at day, summoned 500 ms after `play` started (new scenario field `spawnAfterMs`), goal "kill 3 husks".
- `sculk bench --view first|third|first,third` runs each scenario per camera through the in-game agent's `game_thirdperson` option and puts the original back at the end (also with `--keep` and on error); reports carry `view` and the table a `view` column. Without an agent it exits 2.
- `sculk bench` writes every run's per-tick fight trace to `<report>.trace.json` (`tracePath`: every mob's distance, reach, cooldown, view offset and closing speed, the footwork, plan, shield, aim error and what happened in that tick) and adds combat extras from it (`stepBacks`, `idleInReachMs`, `inReachMs`, `shieldMs`, `retreatMs`, `advanceMs`, `holdMs`, `maxMobsInReach`, `aimErrAtSwing`) plus `misses` and `crits`.
- `sculk bench` waits for the world on installs the user starts by hand (new `--wait <seconds>`, default 900) instead of failing at attach, and uses an agent another process already attached.
- `game_query` `blocks` and `block`, and `container`, no longer fail near the world floor or build limit: rows outside the dimension's height range are left out (`[]` or `null` when wholly outside).
- `game_launch` takes `worldWaitSeconds` (default 180, up to 1800) and `keepOnTimeout`: with it, a world that has not loaded in time leaves the game running with a manual step to enter it, and `game_status` turns ready once the world is in. `sculk game check` takes `--world-wait`.
- The helper pack reports the player from the newest spawn when the world lists more than one handle.
- `game_command` through the script debugger no longer takes 5 s while a `play` job or other helper queries run (measured 5.06 to 5.08 s against 0.53 s when quiet): the wait for a command's output counted the helper pack's own traffic (each query's echo, confirmation and reply) as output, so it never went quiet, and those lines no longer appear in the command's `output`. `sculk bench` sends its commands through the in-game agent when the engine route is used (a reset takes a few seconds instead of about 25).
- `sculk bench --stance auto|kite|guard` (or a comma list) sets the fight's shield stance on every scenario's `play`/`fight` action and runs each scenario once per stance, with a `stance` column in the table and `stance` in the JSON and trace.
- New combat scenario `cornered`: 3 zombies against a player in a dead-end stone alcove, where stepping back is impossible.
- Combat extras: `blocked` (shield blocks from the play stats), `blocks`, `stepBackShare` and `inReachStillMs` from the trace; `idleInReachMs` no longer counts time standing behind a raised shield.
- The helper's player state carries `offhandDamage`, the durability damage of the off-hand item (a shield gains 4 with each husk hit it blocks, measured on 1.26.63).
- Fixed: the bench found late-spawned mobs with one look 250 ms after the summons, so `husks3` reported 0 kills when the husks died first. It now looks every 100 ms for up to 3 s, and counts a player kill of the right type for a mob it never saw.
- Engine calls made one after another no longer take about 57 ms each (measured on retail: `input.move`, `input.look` and `player.state` 25 ms apart, 56 to 58 ms each, while a call after 160 ms of silence took 6 ms): the agent sent every answer as two writes (the line, then its newline) with Nagle's algorithm on, so the newline waited for the client's delayed ACK. Each line is now one write and the agent sets `TCP_NODELAY` on every connection; a call costs its handler's own time.
- The agent's tick stream no longer keeps reporting the player at the old world's spawn after a world change (a left world, a failed join, a rejoin): the client tick now reads the local player only through a registry the game used in the last client frame, newest capture first, so the stream follows the new world's player within a frame or two, and `player.state` reads that same registry. A `tick` sent while the agent has no current reading of the local player carries `position`, `rotation`, `velocity` and `onGround` as null instead of the last position, so the client skips it.
- A session that changes worlds a third or fourth time keeps its tick stream: the agent now reuses the slot of a game object it no longer sees stepping, instead of running out of slots and never recognising the new world's server.
- `input.attack` and `input.use` no longer miss about one click in three with the crosshair steady on a mob (measured on retail on a husk held still 2 blocks away: 13 of 20 attacks saw it before, 20 of 20 after; sampled every 17 ms the pick read entity, entity, nothing in every tick): the game's crosshair pick is empty in one frame of every tick, so a click that finds it empty now waits for the next main-thread drain that holds it (at most 75 ms) and reads the target and clicks there. A click sent within a tick of a view change still sees the old view's target: the game computes the pick once a tick.
- `sculk bench goal|task`: ten phrasings per intent (kill, reach, two steps, smelt and craft, trade, a diamond in a blocked chest, a crafting table 30 blocks away, a nested shulker box) measure what the goal grammar understands and whether the steps get it done. Measured with a decision model placing what the grammar could not, and with it setting the fights' stance: no clear difference in 90 goal and task phrasings and 40 fights each way (`docs/bench.md`, Latest Results), so sculkwire asks no model.
- `play` compiles its goal into a plan with a deterministic grammar: steps in order (kill, reach, hit every X, craft, smelt, trade, fetch, also out of a shulker box in a chest, equip, go to a block or a mob, survive) and a stance from the goal's words ("with the shield up", "keep your distance"). Task steps run inside the job as code with typed results: they walk to the nearest station, drive its screen, measure what the inventory gained, and make or fetch a missing ingredient first from a recipe index built from the cached vanilla recipes and the project's own. A hostile within 6 blocks or a hit interrupts a step, the player fights, and the step is tried again (at most 2 retries). The result has `plan` (per step: kind, status, message, task actions and inventory change), and `player_job` progress names the current plan step.
- `fight` swings only when the mob is within the measured strike reach: a centre distance of 3.0 blocks strikes and 3.1 does not (retail 1.26.63, view on the chest), where the code assumed 3.3. Swings from 3.0 to 3.3 could never land. At a mob walking in the swing waits for 2.9, with no lead for its walk: of about 1,900 traced swings at a mob walking in, 5% landed from 3.05 or more, 48% at 2.9 and 76% at 2.85.
- `fight` fights a group in one loop: it changes target without stopping, strikes whichever mob in reach can take a hit (each mob has its own hit cooldown), waits for chasing mobs at the edge of reach, gives ground whenever any mob (not only the target) would get it in reach, and no longer sprint-jumps into a pack. `play` runs one continuing `fight` step for a group instead of one per mob.
- `fight` and `play` take `stance` (`auto`, `kite`, `guard`). `kite` is footwork only. `auto` (default) is the same footwork, with the shield only when boxed in (under 1 block of free run behind), raised 400 ms before the attack due by that mob's attack clock. `guard` keeps the shield up with a melee mob within 3.6 blocks, strikes only in the window after a block and steps out when no window opens. Measured on 1.26.63: a shield blocks only after 6 ticks up and inside 90 degrees, a zombie attacks every 20 ticks (30 after a blocked hit), and a swing opens the shield for 12 ticks, which is why standing behind it against three mobs takes more hits than stepping back (`docs/bench.md`, Latest Results).
- `fight` and `play` report `blocked`: hits the shield took, read from the off-hand durability.
- `fight` never stands where the hand cannot answer: the feet hold only while the hand can strike, this tick, every mob coming in inside the strike range (the swing ready and the view on it). Otherwise the player walks back at once, keeps turning and strikes on the way. Among mobs in reach the one the hand can strike soonest is the target, and a crit jump needs 4.5 blocks clear of every other mob. Measured in the trace: mob hits land with the attacker 1.6 to 2.5 blocks away as the fight reads it.
- `player_act` on the engine route: the camera keeps one view in flight and sends the newest when the agent answers. With up to 8 in flight, 120 looks a second queued behind the agent's one look per game frame, so after a target change the game's view stood still for 100 to 200 ms and then jumped (seen in the fight trace as an aim error frozen at 25 to 60 degrees with the swing ready).
- `fight` against a creeper: the creeper lights when the gap between its box and the player's is under 2.5 blocks (centre distance 3.1 along an axis, 3.35 on a diagonal) and coasts about 0.25 more, so from the side it stands just outside the 3.0 strike reach. `fight` closes that gap in 1 to 3 ticks while the creeper slows, swings within about 200 ms of it lighting, and backs straight off without turning (4.32 blocks a second, past 7 blocks about 0.7 s after the hit, where turning round to sprint took 1.4 s). One decision per fuse, the keep-out from other mobs stays on while the creeper is the target, and the shield is raised against the blast only when the walk cannot make it.
- Engine-route movement no longer waits for the agent's answer, so the fight loop keeps its 25 ms pace while moving.
- sculkwire opens its own test world by the world's icon: `createWorld` writes a `world_icon.jpeg` that encodes the level id, and the join recovery opens only the tile whose thumbnail shows it. It never opens a tile by its position, never clicks the Play screen's tab strip, presses Save & Quit only by its name, and stops with a reason when the tile is not found.
- `game_launch` on an install you start yourself: start the game, and sculkwire attaches its in-game agent and opens the test world from the start screen.
- `sculk bench` reports how the world was reached (`entry`: `launch`, `auto-enter`, `manual` or `already-open`, with the seconds from the bridge's start and the inputs sculkwire sent walking the menus), in the JSON and under the table.
- `goto` no longer gives up when the first 48 by 48 block window holds no way. It plans again over 80 by 80 and 128 by 128 blocks, then walks to the closest reachable spot and plans again while each leg gets at least 1 block nearer. A goal sealed in by blocks fails at once, and the failure says which window it searched, how many legs it walked and how close it got.
- Task steps (craft, smelt, fetch, trade, `reach_block`, `reach_entity`) look beyond 16 blocks when nothing is near: 16-block cubes on a ring around the player out to 48 blocks for blocks, a 48-block radius for entities. A miss says how far it looked (`no crafting table within 48 blocks (searched 9 cubes)`).
- `game_query` `blocks` takes `types`, a list of block ids matched in one scan.
- Task steps use a station, chest or trader from where they can: each visible face, then up to 4 standing spots around it (12 uses and 30 s per target), and they refuse a screen that opened for a different chest or trader (`container.open`'s position, the trade screen's trader id).
- New bench scenarios: `nav/detour`, `nav/sealed`, `task/far-table`, `task/blocked-chest`, `task/blocked-chest-villager`.
- `game_settings` through the agent takes 0 or 1 for an on/off option, as the `options.txt` route does (`sculk game settings set gfx_fullscreen 1` was refused with "this option takes true or false" while the agent was attached).
- Task steps wait for the inventory screen before a 2 by 2 craft and retry a screen that is not readable yet (falling back to a crafting table near), report the helper's query errors instead of "none found", and fetch every item when the goal gives no number (`took all 3 diamond`).
- `sculk bench` fails a run whose build or reset command the game rejects as a syntax error or an unknown command, with the game's text, instead of going on without what the command was to make.
- `play` no longer idles to the time limit on a goal it did not understand: it runs the steps it placed, defends itself, and stops with `goal_unknown` 5 s after there is nothing to do, quoting the part it did not understand and listing the goal forms it knows with an example each. A goal that says to survive, defend or wait still runs to its time ("survive for 30 seconds"); a duration alone does not make a goal understood.
- Task steps read item phrases the way a player writes them: material words ("wood pickaxe", "a pickaxe out of the planks"), trailing words ("made at the table over there"), and a bare "pickaxe" or "sword" takes the best variant that can be made from what is at hand, saying which and why.
- `fetch` re-reads every container after each round (a placed shulker box included) and ends "all" only when it has every item the first read showed, places a shulker box on the first free cell a view reaches (several cells and spots, naming each refusal), and bench run records carry each task step's actions (`steps`).
- `play` no longer idles while a kill step's target is alive within 24 blocks: when no other tactic is offered (the target keeps away or walks off, or the player is low on health and it is not at hand), it goes after the nearest goal target at a low score that any flee or meal still beats.
- `fight`: zombies and husks holding a spear are fought the way the spear works (it hits on contact at about 2.5 blocks, and only while the two close faster than about 0.9 blocks a second): the feet give ground while one charges, so its spear cannot hurt, and the hand strikes it on the way; no critical jumps near one; one backing off to its 9 to 11 blocks is chased; a fight over all hostile mobs no longer ends while a struck mob is alive within 24 blocks. The helper reports a mob's main-hand item (`held`), reading a spear with the `hasitem` selector when the Script API gives no equipment for the mob, and a mob that hurts the player from 2.3 blocks or more is fought as a spear mob from then on. No shield is raised against a spear mob: its hit goes through. New bench scenario `combat/spears3` (a scenario mob takes `held`).
- `play` kill steps count targets that another mob killed within 24 blocks (spear husks run each other through) toward the goal, reported apart from the player's kills (`goal done: 3 of 3 husk dead (2 killed by the player, 1 by another husk)`, `stats.otherDeaths`), and stop with `targets_gone` once none of their targets is left within the radius before the count is reached, instead of waiting for the time limit.

- In-game agent (`engine_attach`, `engine_status`, `engine_command`, `engine_player`, `engine_tick`, `engine_screenshot`; `sculk engine attach|status|command|tick|screenshot|player`). A small DLL is injected into the running retail game: under the install's Wine or Proton prefix on Linux and macOS, natively on Windows. It serves newline-delimited JSON-RPC 2.0 on `127.0.0.1:19160`, runs every request that touches the game on its main thread, and resolves its addresses from anchors at attach time, so it is not tied to one build. The DLL is built from `native/` with cargo (rustup's `x86_64-pc-windows-msvc` target, no Windows SDK) or, without cargo, downloaded from the release with its sha256 checked. Hot reload unloads the old copy completely before the new one loads. `engine_command` works right after an attach: the agent replays a real player command's origin, typing `/testfor @s` in chat itself the first time, only while the HUD alone shows. `engine_screenshot` copies the frame the game presents into a PNG at your path, open screens included, without the game's own screenshot (no toast, nothing in its gallery). See [In-Game Agent](docs/engine.md).
- Input lock (`game_input_lock`, `sculk game lock`): keeps your own keyboard, mouse and controller out of the game while sculkwire plays through the agent, with `on`/`off`/`auto` modes, F9 to take control and give it back, the game's own camera permission, an action-bar badge, and the desktop focus watcher of a window-mode game. The lock fails open, also when the agent unloads. `player_act` and `sculk bench` use the engine route through the built-in input provider while the agent is attached; `input.attack` and `input.use` report the crosshair target and hold their button on request, so `player_act mine` breaks blocks on the engine route.
- Game settings (`game_settings`, `sculk game settings`): the game's own options by their `options.txt` tag, changed through the game when the agent is attached and in the file when it is not, with every changed value put back by `game_stop`. Both routes answer in the game's units (`gfx_viewdistance` in chunks), and the int-choice options such as `game_thirdperson` work through the agent.
- World settings (`world_settings`, `sculk world settings`): game rules, difficulty, game type, time and weather of a test world, through the game when attached and in `level.dat` otherwise, and only ever for `sculkwire-*` worlds.
- Menus and screens (`game_ui`, `sculk game ui`): the current screen and its stack, its controls, and keys, text, clicks and scrolling through the game's own UI, so menus work in the background and on Windows without the foreground. Every input is refused on a store, Marketplace, Minecoins, Dressing Room or persona editor screen except `Escape`; on OreUI pages the agent reads the page's route and allows clicks only on the Play screen and the Settings option pages. A click the game did not read is reported (`ui.click_input`). `game_input` and the `game_launch` sign-in recovery take this route while the agent is attached.
- Inventory, containers, crafting and stations (`player_inventory`, `container`, `craft`, `interact`, `screen`; `sculk player inventory`, `sculk container get`, `sculk craft match|run`, `sculk interact block|entity`, `sculk screen state|move|act|close`): the player's inventory, attributes and armour and any block container, with enchantments by name and the contents of shulker boxes and bundles; recipe matching through the game's own lookup; using a block or an entity like a right click, with `changed` when the used block's state changes (a lever, a button); and the open screen's containers and state, moving items (also into a bundle, through the game's own bundle insert, and on crafter, hopper, dispenser and dropper screens) and running its own action (craft 2x2 and 3x3, trade, stonecut, smelt, enchant, anvil, grindstone, smithing, loom with the requested pattern, cartography, beacon, brewing) as the game's own item requests; `screen close` closes the chat screen too. `player_inventory` and `container get` fall back to the helper pack without the agent.
- Extensions can supply the agent DLL for game folders they recognise (`registerAgentSource`). CI builds the agent for `x86_64-pc-windows-msvc` on Linux and Windows, and the release publishes `sculkwire-agent-<version>-x86_64-windows.zip` with its `.sha256`.
- `sculk mcp` answers every request it already received when the client closes stdin, and exits only after the answers left stdout (at most 30 s). Before, a client that wrote its requests and closed stdin at once could get a cut-off answer when it read slower than the pipe buffer filled.
- `player_act` drives a Linux desktop-mode game through the attached agent, `select_slot`, `hold` and `mine` included; before, every action asked for window or headless mode.
- `player_job`: every ended job names its `stopReason` (the play loop's own stop, or `error` when the run failed).
- `game_status` follows the game process, so a crashed game is no longer `running` or `ready`, and the `/connect` manual step shows only while no `/connect` client is attached.
- `game_registry` falls back to the helper pack's Script API when `/connect` answers an empty list (the retail game does). `game_input` reports its route, and `game_reload` no longer promises a rejoin.
- `game_reload` and `game_launch` copy the project's packs over the project's existing folders. Before, a folder left by an earlier launch was reused as it was, so edits never reached the game.
- `game_launch` width and height set the game's resolution under gamescope.
- Game files tools find the game folders of every detected Wine or Proton client install, not only mcbe-gdk-linux.
- Knowledge lookups suggest near names for misspelt ids (`gvie` suggests `give`), and stable Script API symbols are described from the plain typings.
- `script_profile` places native bindings at their call site, and BDS session packs report path `.` when the project folder is the pack.
- `play` names the carried food at full hunger instead of `Food: none`.

## v0.1.0

First release.

- Versioned knowledge for stable and preview: docs, Script API, components, commands, Molang, vanilla examples and changelogs.
- Pack validation with file, line, column and rule code for every problem, including Regolith projects.
- Schemas from [rockide/schemas](https://github.com/rockide/schemas) by default, kept on rockide's newest GitHub release: the source tarball of the newest release tag goes into the cache on first use, the tags are checked again at most once a day (`sculk knowledge update` checks at once), a new release is unpacked and checked before it replaces the old copy, and the last copy is used offline. Without a copy, validation goes on with the engine schemas and `component_lookup` without rockide, and both say so in a `rockide.note`.
- The validator tries rockide first, then the engine schemas from bedrock-samples. Measured on vanilla 1.26.60.5: rockide covers 7476 of 7862 JSON files (the rest are texture lists, `texts/languages.json` and manifests, which have their own check), and 86% of injected entity, block and item errors are caught instead of 18% with the engine first (unknown components and fields), for 9 more held-out vanilla false positives in 3816 files. `--rockide <dir>` (CLI) and `rockide_dir` (MCP) pick a checkout. Results carry `rockide` (release, commit and newest release seen).
- Loot `match_tool` conditions accept a number or `{range_min, range_max}` for `count`, `durability` and enchantment `levels`, as Mojang documents.
- `component_lookup` and `sculk component` include the rockide definition per scope (entity behaviors and components, block and item components, client files): description, properties with types, defaults, allowed values and bounds at the `format_version` matching the channel's game version, plus every version and the versions where it changed.
- Every data source updates on its own, at most one cheap check per source per day, without blocking a tool call and keeping the last copy offline or after a failure. The version pins (samples tags, npm builds, BDS builds, changelog titles) are re-resolved in the background once a day. The MCP server then checks out a newly pinned samples tag while the previous checkout answers, downloads a newer BDS build for the next `bds_check`/`gametest_run`/session, fetches changelogs again when a new article appears and re-indexes the creator docs when `main` moves, all in the background. New typings are installed on next use with the previous install as fallback. A CLI command only refreshes the pins in the background and exits at most 3 seconds after its output; `sculk knowledge update` refreshes everything in the foreground, including installed BDS builds.
- `sculk knowledge status` and `knowledge_versions` list every data source with the version in use, the newest seen upstream and the last check.
- Bedrock Dedicated Server: load checks, headless GameTest runs, sessions and script profiling. A Regolith project whose profile runs filters is built with rgl first and BDS loads the built packs; diagnostics point at the source files (through source maps for generated scripts), and a failed build is a `regolith.build-failed` error with no server started.
- Live game bridge on Windows and Linux: private single-player test worlds, deploy and reload, content log, queries, screenshots and input, with screen-aware sign-in recovery at launch. Deploys leave one folder of the project per pack uuid (a fresh build goes into the project's rgl export folder when there is one) and warn about other packs that share the uuid.
- Player control (`player_act`, `player_job`, `player_state`): human-like camera, pathfinding and combat skills, and the background `play` loop with an optional decision model as advisor.
- Game files of an installed PC (GDK) copy (`game_builds`, `game_vanilla_packs`, `game_extract_pack`, `sculk gamefiles`): game version, the per-version `vanilla_1.x` packs and their extraction from `.brarchive` into plain folders.
- Extensions: packages listed in `SCULKWIRE_EXTENSIONS` or placed in `<config>/extensions` add MCP tools, CLI commands and an in-process input provider for `player_act`; a broken extension is skipped with one stderr line. An extension may also supply the in-game agent's DLL for game folders it recognises (`registerAgentSource`), which replaces the built-in build at attach.
- `sculk bench` measures the player skills in built arenas.
- Installers. `install.sh` (Linux and macOS) and `install.ps1` (Windows) install the newest release into a managed layout, put `sculk` on PATH and run `sculk setup`. Flags: `--yes`, `--decision`, `--register`, `--channel`.
